### 1.1 jar 构建时机边界（消除"每次运行都打 jar"）

> 明确结论：**jar 只在两类时机构建一次**（① 后端代码变更后；② 生成新版演示交付物时），运行阶段直接 `java -jar` 起用，前端改动不再触发打 jar。

| 变更类型 | 是否打 jar | 动作 | 生效方式 |
|---|---|---|---|
| 前端页面/交互代码变更 | ❌ 不打 | `npm run dev` 热更新（模式一）；或 nginx 替换 static（模式三）；模式二需出**新版交付包**才打 | 秒级/分钟级 |
| 后端 Java 代码变更 | ⚠️ 构建后重启一次 | IDE Run 主类（免打包）或 `mvn package` 后重启该服务；此后全天运行不再构建 | 重启该进程 |
| 后端依赖/配置（pom/env）变更 | ⚠️ 同上 | 重新 `mvn package`（依赖变化必须打包） | 重启该进程 |
| 仅数据/演示数据变化 | ❌ 不打 | 直接 SQL/脚本灌入，jar 不动 | 即时 |
| 版本发布（演示包/生产包） | ✅ 打（发布物） | `npm build && mvn package` 产出带版本 jar/包归档 | 按发布节奏 |

**各模式的实际频率**：
- 模式一：后端 jar 起一次 = 一个工作日（改后端才重启）；前端全程热更新
- 模式二：同一版本包多次演示复用；仅版本迭代时重打
- 模式三：前端发版不触后端；后端按月/版本滚动升级

## 二、模式一：日常研发（真实业务场景设计）

> 业务场景：警务项目团队日常开发/联调——前端页面开发、后端接口联调、双工作台功能验证、Agent 与大模型联调、数据源/工作流/CDC 等数据能力开发，均在本机 :8080 后端 + :5173 热更新前端下完成。

### 2.1 场景与分工（真实使用方式）
| 开发场景 | 打开终端 | 说明 |
|---|---|---|
| A. 前端页面/交互开发（警务实战/专案/数据中心等 40+ 页） | 仅前端 dev | 改 Vue 秒级热更新，`/api` 全部代理到后端 8080，接口联调不打断 |
| B. 后端接口开发/修复（新增 usercenter/专案等 API） | 后端 + 前端 | 改 Java → 重启后端 jar（或 IDE 热部署）→ curl 冒烟 → 前端验证 |
| C. Agent/大模型联调 | 后端 + 前端 + 真实模型 | 配置页填真实模型 baseUrl/apiKey（内网私有化 vLLM/Ollama 或经审批外网模型）→ 对话验证工具编排/权限继承/密级守卫；未接入模型时 Agent 明确提示不提供伪应答 |
| D. 数据能力联调（数据源插件/工作流/湖仓/CDC/血缘） | 后端 + curl | 起好 MySQL/湖仓后按各模块 API 冒烟（回归脚本兜底） |
| E. 双工作台权限联调 | 浏览器双账号 | admin 管理员端 + police 用户端并行验证五级权限与受控查询 |

## 四、模式三：生产运行技术方案（真实生成，可执行）

### 4.1 部署拓扑（本项目实际单元 + 双节点）
```text
                 nginx :80/443
        /static/  → html 目录(版本化)     /api/ → upstream app-cluster
                                     ┌──────────────────────┐
                    主应用A :8080 ◀──┤ upstream(探活轮询)    ├──▶ 主应用B :8080
                                     └──────────────────────┘
   拆分服务: platform:8091 security:8090 data:8092 police:8093 agent:8094 dev:8095
      （与主应用同机部署；Nacos 注册，NACOS_ENABLED=true）
   共享: MySQL:3306(主)/3307(从) · Nacos:8848 · Kafka:9094 · CH:8123 · Redis:6379
   湖仓: 绝对路径 data/lake-iceberg(双节点挂同一共享目录)
```

### 4.2 统一运行环境（.env / 启动参数，双节点一致）
```bash
# /opt/temporedata-guard/.env（真实值）
SPRING_PROFILES_ACTIVE=prod
DB_HOST=db-internal     DB_PORT=3306   DB_NAME=temporedata
DB_USERNAME=zyapp       DB_PASSWORD=<内网凭据>
NACOS_ENABLED=true      NACOS_ADDR=127.0.0.1:8848
EVENT_BUS_TYPE=kafka    KAFKA_SERVERS=127.0.0.1:9094
# 每节点各自
SERVER_PORT=8080        # 节点B=8081
LAKEHOUSE_WAREHOUSE=/opt/temporedata-guard/data/lake-iceberg   # 共享存储绝对路径
APP_LINEAGE_ENABLED=true  APP_AUDIT_LISTENER_ENABLED=true
JAVA_OPTS="-Xmx512m -Xms256m"
```

### 4.3 systemd 托管（真实单元文件，解决进程回收）
```ini
# /etc/systemd/system/tdg-main.service
[Unit]
Description=Qingzhouyun Main
After=network.target mysqld.service
[Service]
User=zyapp
EnvironmentFile=/opt/temporedata-guard/.env
ExecStart=/usr/bin/java $JAVA_OPTS -jar /opt/temporedata-guard/app/tdg.jar \
  --spring.profiles.active=prod --lakehouse.warehouse=$LAKEHOUSE_WAREHOUSE \
  --app.lineage.enabled=true --app.audit.listener.enabled=true
Restart=always
RestartSec=10
StartLimitIntervalSec=0
[Install]
WantedBy=multi-user.target
```
6 个拆分服务同模板（各自 jar/端口，Restart=always → kill -9 10s 自动拉起）。
`systemctl daemon-reload && systemctl enable --now tdg-{main,platform,security,data,police,agent,dev}`

### 4.4 nginx 双机配置（真实）
```nginx
upstream app_cluster {
  server 10.1.1.10:8080 max_fails=3 fail_timeout=10s;
  server 10.1.1.11:8080 max_fails=3 fail_timeout=10s;
}
server {
  listen 80;
  root /opt/temporedata-guard/web/current;            # 版本目录 + current 软链
  index index.html;
  location /api/   { proxy_pass http://app_cluster; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; }
  location /api/auth/ { proxy_pass http://app_cluster; }
  location /actuator/health { proxy_pass http://app_cluster; allow 10.0.0.0/8; deny all; }
  location /assets/ { expires 30d; add_header Cache-Control "public, immutable"; }
  location /       { try_files $uri $uri/ /index.html; }   # 前端 hash 路由
}
# 发版: 上传 web-v2.1.0 → ln -sfn web-v2.1.0 current → nginx -s reload（零停机）
```

### 4.5 双节点一致性设计（真实做法）
| 事项 | 方案 |
|---|---|
| 前端归属 | 由 nginx 托管（两节点不承担页面差异） |
| 数据库 | 共享主库；主从容灾（4.6） |
| 调度 | 主应用 Quartz 仅 leader 执行：双节点用 `zy_scheduler_lock` 行锁抢占（DB 分布式锁，本项目 DistributedLock 已有 local/Redis 回退） |
| 事件消费 | Kafka 同 group（guard-server）自动分配 → 双节点各消一半；CDC/血缘/审计监听互斥消费 |
| 湖仓 | 两节点 jar 指向同一共享 warehouse 绝对路径（文件锁由 Iceberg ACID 保证） |
| Redis | 血缘缓存/锁共享：主节点 + 从（Sentinel 演进） |
| 会话 | 前端无服务端会话（JWT 无状态），双节点天然可扩展 |

### 4.6 MySQL 主从真实就绪与切换

### 4.7 中间件集群化（真实扩展路径）
- **Nacos**：单机(现有容器, 8848) → 3 节点（复制 nacos 容器 ×3 + shared 集群模式，本项目服务仅注册消费，改造为 NACOS_ADDR=host1:8848,host2:8848,host3:8848 即可）
- **Kafka**：KRaft 单节点(9094) → 3 controller+broker 混合节点（复用现有镜像与 KRaft 配置模板，formatted 后多节点）
- **Redis**：单机(6379) → Sentinel(1 主 2 从 3 哨兵) 或 Cluster
- **ClickHouse**：单机 → 副本表（ReplicatedMergeTree + ZooKeeper/Keeper）
