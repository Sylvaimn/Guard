# 存储层数据模型统一迁移设计文档（TemporeData Guard）

> 版本：v1.0（设计稿）
> 目标：将主库表（已统一 temporedata_guard_*）之外的全部存储层数据模型统一命名，消除 zy_/police 等旧命名残留
> 原则：**分阶段、可回滚、业务数据零丢失**；库/命名空间更名采用"新建-复制-校验-切换"，非原地破坏

---

## 一、现状与统一目标

| 存储层 | 现状 | 统一后 | 变更类型 |
|---|---|---|---|
| MySQL 主库 temporedata | temporedata_guard_*（173 表） | 不变 | ✅ 已完成 |
| MySQL 分析库 zy_analysis | 6 表（业务名）+ zy_lake_meta | **temporedata_guard_analysis**；表：业务名保留，zy_lake_meta→temporedata_guard_lake_meta | 库改名 + 1 表改名 + 代码 3 处 |
| MySQL 归档库 zy_archive | track_point_archived | **temporedata_guard_archive** | 库改名 |
| ClickHouse | police_analysis.track_flow_daily | **temporedata_guard_analysis**.temporedata_guard_track_flow_daily | 库+表改名（代码/查询引用同步） |
| Iceberg 湖仓 | police.track_flow_daily | **temporedata_guard**.temporedata_guard_track_flow_daily | 命名空间+表改名（metadata/快照迁移） |
| Kafka | zy-task/zy-alert/zy-lineage/zy-cdc/zy-quality | **tdg-task/tdg-alert/tdg-lineage/tdg-cdc/tdg-quality** | topic + 消费组 + 事件代码同步 |
| ES 索引 / PG 向量 | temporedata_guard_entity / _entity_vector | 不变 | ✅ 已完成 |

> 命名规范：MySQL 库/表 `temporedata_guard_*`（下划线）；Kafka topic 采用短前缀 `tdg-*`（topic 名过长不利于运维，且与本项目 jar 命名 tdg- 一致）。

## 二、MySQL 分析/归档库迁移

### 2.1 分析库 zy_analysis → temporedata_guard_analysis
- 数据模型：case_stats_daily / fund_flow_stats / track_flow_daily / track_point_partitioned / watch_alert_daily（业务分析表，**保留原名**——无 zy_ 前缀且为主业务模型名）+ zy_lake_meta → temporedata_guard_lake_meta
- 步骤：
  1. `CREATE DATABASE temporedata_guard_analysis`（同字符集/排序）
  2. 逐表 `RENAME TABLE zy_analysis.t  → temporedata_guard_analysis.t`（或 CREATE+INSERT+校验+RENAME，视量级）
  3. `zy_lake_meta` → temporedata_guard_lake_meta
  4. 校验行数一致 → 保留 zy_analysis 空壳一个发布周期后 DROP
- 代码联动（3 处 `zy_analysis.` 前缀）：
  - UserCenterService 受控查询 `zy_analysis.` + table
  - IngestionOffsetService 对账 `zy_analysis.`
  - LakehouseService/CDC 相关源库引用（统一到新库名）

### 2.2 归档库 zy_archive → temporedata_guard_archive
- track_point_archived 随库迁移（同 2.1 流程）

## 三、ClickHouse 迁移

- 现状：`police_analysis.track_flow_daily`
- 目标：`temporedata_guard_analysis.temporedata_guard_track_flow_daily`
- 步骤：
  1. `CREATE DATABASE temporedata_guard_analysis ENGINE=Atomic`
  2. `CREATE TABLE ... AS police_analysis.track_flow_daily`（同结构）+ `INSERT ... SELECT`（或 RENAME TABLE 库间需搬迁）
  3. 校验 COUNT/抽样一致 → 旧库一个发布周期后 DROP
- 代码联动：聚类/分析查询 SQL 中 police_analysis → 新库名

---

## 四、Iceberg 湖仓迁移

- 现状：warehouse/data/lake-iceberg/police/（表 track_flow_daily，快照可时间旅行）
- 目标：命名空间 `temporedata_guard`、表 `temporedata_guard_track_flow_daily`
- 步骤：
  1. 湖仓 API 支持命名空间参数（LakehouseService 常量化 namespace/table）
  2. 数据迁移：读旧表（时间旅行全量）→ 写新命名空间表（新名）
  3. 校验行数/快照 → 更新启动参数 warehouse 不变、表引用新名
  4. 旧 police.* 保留一周期后清理
- 联动：湖仓管理/工作流湖仓节点/CDC 入湖/CdcIngestionListener 目标表名、上传即血缘自动关联目标表名、`temporedata_guard_lake_meta`

---

## 五、Kafka 事件总线迁移

- topic：zy-task/zy-alert/zy-lineage/zy-cdc/zy-quality → tdg-task/tdg-alert/tdg-lineage/tdg-cdc/tdg-quality
- 消费组：qingzhouyun / qingzhouyun-cdc / qingzhouyun-quality → tdg / tdg-cdc / tdg-quality
- 步骤：
  1. 生产端（EventBus kafka topic 常量/注解 @KafkaListener topics）+ 消费端同步改
  2. 新建 topic（tdg-*，分区数同旧）
  3. **灰度**：双写双读一周期（旧 topic 消费位点续传完成存量）→ 切换 → 旧 topic 保留一周期
- 风险：位点/消息积压——需在低峰窗口切换，CDC 位点（temporedata_guard_ingestion_offset）不丢失
- 代码联动：EventBus topic 常量、@KafkaListener（CdcIngestionListener/RealtimeQualityListener/KafkaEventListener/KafkaLineageListener）、config EVENT_BUS_TYPE

## 六、执行顺序与回滚

| 阶段 | 内容 | 回滚 |
|---|---|---|
| P1 低风险 | Kafka topic 双写双读 → 切换 | 回切旧 topic |
| P2 | MySQL 分析库/归档库迁移（RENAME 原子） | 库 rename 回退（同命令反向） |
| P3 | ClickHouse 库表迁移 | 旧库保留至确认后删除，可恢复 |
| P4 | Iceberg 湖仓重建命名空间 | 旧 police.* 保留，参数回退即恢复 |
| 每阶段 | 回归 44/44 + 对应功能冒烟（CDC/对账/受控查询/血缘/湖仓/报告） | - |

## 七、风险与对策
| 风险 | 对策 |
|---|---|
| CDC 入湖目标表名变更丢数 | 先停 CDC 消费者 → 迁移 → 恢复（位点续传） |
| 湖仓快照历史丢失 | 时间旅行读旧表导出→新表（保留旧 warehouse 目录直至验收） |
| Kafka 消息双读重复 | 消费幂等（入湖/血缘登记均幂等：去重键已设计） |
| 分析库改名的外部引用遗漏 | grep zy_analysis/police_analysis/police. 全仓审计 + 回归 |
| 敏感期误操作 | 全流程 git 分支 + DB 快照 + 每阶段独立 commit |
