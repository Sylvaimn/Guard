# 金盾智云警用大数据中台 · 系统运行方案设计文档

> 版本：v1.0
> 输入：技术架构（后端与基础设施服务详细设计文档 v1.0 + v2.1 双工作台落地）+ 业务实际需求（警务实战/数据研判/受控查询/密级管控/专案协同）
> 定位：面向 **开发联调、演示验证、试点部署、生产运行** 四类环境的运行方案选型与部署设计

---

## 一、技术架构现状（运行方案输入）

### 1.1 应用层
| 组件 | 技术 | 运行形态 |
|---|---|---|
| 主应用（全量能力 + 前端静态内嵌） | Spring Boot 2.7 · Java 11 · jar 190MB | 独立进程 :8080 |
| 拆分服务 ×6（platform/security/data/police/agent/dev） | Spring Boot · 共享 MySQL | 独立进程 :8090-8095 |
| 网关（可选） | Spring Cloud Gateway | :8088（lb:// Nacos） |
| 前端 | Vue3 构建产物 → 主应用 static 内嵌 | 无独立部署 |

### 1.2 基础设施（Docker 容器）
MySQL 8.0（:3306 主 / :3307 从，binlog ROW 复制，业务库 temporedata 155+ 表 + zy_analysis 分析库）· Nacos 2.4.3（:8848）· Kafka 3.7 KRaft（:9094）· ClickHouse（:8123）· Prometheus（:9090）+ Grafana（:3000）· Redis（:6379）· Iceberg 湖仓（本地 HadoopCatalog data/lake-iceberg）

### 1.3 运行约束（实测经验）
- 开发机 8GB 内存/8 核：主应用 Xmx512m + 6 服务各 Xmx192m + 容器 ≈ 6GB —— **资源临界**
- 主应用长驻进程可能被宿主回收 → 需 nohup+disown / systemd / supervisor 托管
- 旧 Gradle 系统与 8080 端口冲突风险 → 端口与进程治理
- Docker Desktop 内存 5GB 配置

## 二、业务实际需求 → 运行要求映射

| 警务业务需求 | 运行要求 |
|---|---|
| 7×24 情报检索/布控预警可用 | 高可用 + 快速恢复（服务托管、健康检查、自愈） |
| 涉密数据（L1-L4）不出域 | 私有化部署、物理/网络隔离、最小暴露 |
| 密级/数据范围/审计（查询留痕） | 权限内核 + 全链路审计日志可靠落库 |
| 受控查询与专案协同（多人并发） | 会话/事务一致、连接池充足 |
| CDC 实时采集（binlog→Kafka→湖仓） | Kafka 与主从 binlog 稳定运行、位点可续 |
| 湖仓/ClickHouse 分析 | 磁盘容量与快照治理 |
| 突发事件研判峰值（重大案件） | 弹性扩容预案（主应用多节点 + 网关负载） |
| 演示/验收（上级检查） | 一键启动脚本、演示数据、可视化监控 |

## 三、运行方案选型

### 3.1 候选方案对比
| 方案 | 形态 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 单机 Docker Compose | 全部容器 + jar 进程 | 部署简单、开发演示快 | 单点、性能受限 | **开发/联调/演示** |
| B. 双机主备（应用双节点 + MySQL 主从） | 2×应用主机 + 主从库 | 高可用、成本适中 | 需 Nacos/Kafka 集群化 | **试点/地市部署** |
| C. K8s 容器云 | 全部容器化编排 | 弹性/自愈/标准化 | 运维门槛高、信创适配成本 | 省级/集团级 |
| D. 国产化信创（鲲鹏/麒麟 + 达梦/人大金仓） | 迁移适配 | 合规 | 适配工作量大 | 政法信创要求 |

### 3.2 推荐：分环境两套方案
```text
环境1 开发演示（当前硬件即可）
  方案 A：Docker Compose(MySQL/Nacos/Kafka/CH/监控) + systemd/脚本托管 7 个 jar
        → 启动脚本一键拉起 · 健康检查 · 日志统一

环境2 试点/生产（2 台以上服务器，推荐）
  方案 B：应用双节点 × Nacos 集群 × Kafka 集群 × MySQL 主从 × Redis
        → 网关 8088 负载均衡 · 任一节点故障自动切换 · 从库容灾
```

## 四、方案 A：开发/演示环境运行设计（推荐立即采用）

### 4.1 组件清单与资源分配（单机 8GB/8 核基准）
| 组件 | 数量 | 内存建议 |
|---|---|---|
| MySQL 主 | 1 | 容器 1.2GB（innodb_buffer_pool 512M） |
| Nacos / Kafka / ClickHouse / Redis / Prometheus / Grafana | 各 1 | 合计 ≈ 2GB |
| 主应用 jar :8080 | 1 | Xmx512m -Xms256m |
| 拆分服务 :8090-8095 | 6 | 各 Xmx192m（合计 1.2GB） |
| 合计 | - | ≈ 6GB（预留 2GB 系统） |

### 4.2 进程托管（解决"进程被回收/手工 nohup"痛点）
推荐 **launchd（macOS）/ systemd（Linux）** 托管 7 个 Java 进程：
- 自动重启（异常退出拉起）
- 开机自启
- 日志落盘滚动
- 健康检查（每 10s curl /actuator/health）

**启动脚本（scripts/start-cluster.sh 已有雏形，补齐）**：
```bash
start-all.sh    # 拉容器 + 启 7 进程(等待健康) + 打印访问地址
stop-all.sh     # 优雅停机
status.sh       # 端口/进程/健康一览
```

### 4.3 环境变量清单（统一 .env 注入）
```
SPRING_PROFILES_ACTIVE=prod  DB_HOST=127.0.0.1  DB_PORT=3306  DB_NAME=temporedata
DB_USERNAME=root  DB_PASSWORD=***  NACOS_ENABLED=false
EVENT_BUS_TYPE=kafka  KAFKA_SERVERS=127.0.0.1:9094
--app.lineage.enabled=true --app.audit.listener.enabled=true
--lakehouse.warehouse=/opt/temporedata-guard/data/lake-iceberg(绝对路径)
```

### 4.4 演示准备
- 内置演示账户：admin(管理员端) / police(用户端 v2.1)
- 演示数据已预置：专案/对象/线索/报告/收藏/查询历史/湖仓/CDC 位点
- 一键演示场景脚本（police-combat-test.sh 44 项回归可作验收基线）

## 五、方案 B：试点/生产环境运行设计（推荐演进目标）

### 5.1 拓扑
```text
                   ┌── 警务内网访问层(仅内网/VPN, 前端静态亦可独立 nginx)
                   ▼
              Nginx/LB :443(可选, 反代网关+静态)
                   ▼
      网关 zy-gateway :8088 (Spring Cloud Gateway, Nacos lb)
        ├──────────────┼──────────────┐
  主应用A :8080    主应用B :8080   拆分服务×6(可多副本)
        └──────────────┴──────────────┘
   共享: MySQL主:3306 ──binlog──▶ MySQL从:3307(只读/容灾, mysql-dr.sh)
         Nacos 集群(3) · Kafka 集群(3 KRaft) · Redis Sentinel/Cluster
         ClickHouse(副本) · Prometheus+Grafana · 湖仓(共享存储/HDFS)
```

### 5.2 高可用要点
| 层 | 方案 |
|---|---|
| 应用 | 主应用双节点（同库同资源，前端静态随主应用或独立部署）；事件消费组自动负载/互斥 |
| MySQL | 主从 binlog ROW + mysql-dr.sh（backup/status/check/switch/restore）；业务读可走从库 |
| Nacos/Kafka | 3 节点集群（本机 KRaft 已验证单节点，扩 3 即 HA） |
| 网关 | lb:// 服务名轮询；节点故障自动摘除 |
| 湖仓 | warehouse 置于共享存储/NFS/HDFS；快照时间旅行提供数据级回退 |
| 前端 | 内嵌主应用随节点负载；或独立 nginx 托管 static + 反代 /api |
| 备份 | MySQL 全备(每日) + binlog 增量 + 湖仓目录快照 + 配置/文档归档 |

### 5.3 容量建议（试点规模：500 用户/日活 100）
| 资源 | 建议 |
|---|---|
| 应用主机 ×2 | 16C/32GB（各跑主应用+3 服务） |
| 数据库主机 ×2 | 16C/64GB（主从，数据盘 SSD 500GB+） |
| 中间件主机 ×3 | 8C/16GB（Nacos+Kafka+Redis+CH） |
| 湖仓 | 共享存储 1TB 起步（Parquet 压缩 ≈1:4） |

### 5.4 安全运行
- 内网隔离 + 端口最小开放（仅 443/8088）
- 数据库最小账号（应用账号仅业务库 DML，无 DDL/管理）
- Kafka/Nacos 带认证；ClickHouse 账号密码 + IP 白名单
- 全链路审计（登录/查询/导出/Agent 工具）落 zy_audit_log/zy_data_query_log/zy_ai_trace
- 密级管控与脱敏为运行期默认策略（前端 + 后端二次校验）

## 六、监控与运维设计

| 能力 | 实现 |
|---|---|
| 指标 | Prometheus 抓取：JVM/HTTP + 业务指标(zy_query_count/zy_perm_denied/zy_agent_tool_call/ai_chat_total) |
| 面板 | Grafana：平台总览（服务健康/请求/错误率）+ 警务业务（查询量/拒绝量/工具调用/CDC 位点滞后） |
| 告警 | 规则：进程 Down、接口 5xx 率、Kafka 消费滞后、湖仓容量>80%、磁盘>85% |
| 日志 | logback 滚动 + 按服务分目录 + 集中采集（试点可加 Loki/ELK） |
| 健康 | /actuator/health 探活；status.sh 一键巡检 |

## 七、容灾与演练
| 场景 | 处置 |
|---|---|
| 主应用宕机 | 双节点自动切换（网关摘除）→ 恢复后重新注册 |
| MySQL 主故障 | mysql-dr.sh switch 从库升主 → 业务连库串切换（脚本含） |
| Kafka 单点故障 | KRaft 3 节点容忍 1 故障；消息未消费由位点续传 |
| 误删数据 | 湖仓时间旅行回退快照；MySQL binlog 定点恢复 |
| 演练 | 每季度：主从切换演练 + 湖仓回退演练 + 恢复演练报告 |
